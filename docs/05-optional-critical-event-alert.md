# Optional：Windows イベントの Critical を1件以上検知するアラート

[README](../README.md) | [Step1：Azure VM のログ収集](02-azure.md) | [Step2：オンプレミス VM のログ収集](03-onpremises.md)

Windows イベント ログの Critical（重大）を、Event ID や Source を限定せずに検知するログ検索アラートを追加します。既存の Event ID `9001` のアラートは残し、同じ Log Analytics ワークスペース（LAW）とメール通知用アクショングループを使用します。

この章は任意の演習です。**デプロイは Step1 と同じ Azure Portal の操作で行います。** Critical の収集は設定済みの前提で、新しいアラート規則だけを作成します。DCR は変更せず、LAW の「ログ」での確認も行いません。

## シナリオと検知条件

- 対象サーバーで Critical のイベントが1件発生する。
- 直近15分の Critical が1件以上あれば、5分間隔の評価でアラートを発生させる。複数回の発生や連続した違反を待つ設定にはしない。[^3]
- `Computer` ごとに評価し、既存のアクショングループでメール通知する。

Windows イベントの Critical は数値のレベル `1` です。アラートの KQL では `EventLevel == 1` を使用します。[^2]

**「1回でも出れば」は、評価対象の15分間に1件以上あれば発報するという意味です。** リアルタイム通知、過去の全イベントの遡及検知、イベント1件ごとのメール送信を保証する設定ではありません。ログが収集されていない場合や、取り込みが検索期間より遅れた場合は検知できません。

## 始める前に

- Critical を既存 LAW の `Event` テーブルに収集済みで、Event ID `9001` のアラートとメール通知用アクショングループが設定済みであることを前提とします。
- ログ検索アラートを作成でき、対象 LAW の読み取り権限を持つ Azure アカウントを使用してください。
- アラート規則の追加には費用が発生します。Portal の推定コストを確認してください。

### 入力例

| 対象 | 例 |
|---|---|
| サブスクリプション / RG | 既存 LAW と監視リソースの配置先 |
| LAW | `law-arclab` |
| 既存アラート規則（変更しない） | `alert-arclab-event9001` |
| 追加するアラート規則 | `alert-arclab-windows-critical` |
| 既存アクショングループ | `ag-arclab-mail` |
| アラート規則のリージョン | LAW と同じ。例は Japan East |

## 5-1. Critical 用のログ検索アラートをデプロイする

1. LAW の「アラート」から「作成 → アラート規則」を選択します。既存の `alert-arclab-event9001` は編集しません。
2. 「スコープ」が既存 LAW `law-arclab`（`Microsoft.OperationalInsights/workspaces`）であることを確認します。
3. 「条件」で「カスタム ログ検索」を選択し、次の KQL を入力します。

   ```kusto
   Event
   | where EventLevel == 1
   | project TimeGenerated, Computer, EventLog, Source, EventID,
             EventLevel, EventLevelName, RenderedDescription, _ResourceId
   ```

   LAW に収集されたすべての Critical を対象にします。Event ID `9001` や Source `ArcAmaHandson` の制限は付けません。検索期間はウィンドウ サイズで設定します。

4. 測定とアラート ロジックを次のように設定します。[^3]

   | 項目 | 設定 |
   |---|---|
   | 測定 | テーブル行（Table rows） |
   | 集計の種類 | Count |
   | 集計の粒度 / ウィンドウ サイズ | 15分 |
   | しきい値の種類 | 静的 |
   | 演算子 | 次の値より大きい（Greater than） |
   | しきい値 | `0` |
   | 評価頻度 | 5分 |
   | アラートを発生させる違反数 | 1回 |
   | 評価期間 | 15分 |

   **Count が `0` より大きい**設定なので、1件で条件を満たします。「1より大きい」にすると2件必要になるため、本シナリオには使用しません。

5. Step1 と同じ「ディメンションで分割」を設定します。

   | 項目 | 設定 |
   |---|---|
   | ディメンション名 | `Computer` |
   | 演算子 | 含む（Include） |
   | ディメンション値 | 現在のすべての値 |
   | 将来の値をすべて含める（Include all future values） | 有効 |

   これにより各サーバーを個別に評価します。同名のコンピューターがある環境では、`_ResourceId` も分割ディメンションに追加して区別します。

6. 「アクション」で、既存の `ag-arclab-mail` を選択します。通知先や既存の自動化アクションを確認し、演習でそれらを実行してよいことを確認してください。メール受信には受信可能な宛先と、求められた宛先確認が必要です。
7. 「詳細」で次を設定します。

   | 項目 | 設定例 |
   |---|---|
   | サブスクリプション / RG | 既存の監視リソースの配置先 |
   | アラート規則名 | `alert-arclab-windows-critical` |
   | 説明 | 収集対象の Windows イベント ログで Critical を1件以上検知する |
   | 重大度 | 0：重大（Critical） |
   | リージョン | LAW と同じ。例は Japan East |
   | ID | なし（None）。既存手順と同様、規則の最終編集者の権限を使用 |
   | 作成時に有効にする | 有効 |
   | アラートを自動的に解決する | 有効 |

   Windows のイベントレベル `1` と、Azure Monitor のアラート重大度 `0` は別の設定です。アラートの重大度を Critical にするだけでは、Windows の Critical を検索する条件にはなりません。

   ID を「なし」にする場合、最終編集者には対象 LAW の読み取り権限が必要です。運用では、専用マネージド ID と LAW の読み取り権限による継続的な実行も検討してください。[^3]

8. 「確認および作成」で LAW、KQL、Count > `0`、違反1回、`Computer`、アクショングループを確認し、作成します。
9. 作成した規則を開き、条件と通知先が保存され、規則が有効になっていることを確認します。直近15分に Critical が既にあれば、作成後の評価でアラートが発生する場合があります。

確認してみよう。既存の `9001` 用規則と新しい Critical 用規則が、別々に有効になっていますか。

## 5-2. Portal のアラートとメール通知を確認する

1. Portal の「モニター → アラート」で、対象サブスクリプション、RG、時間範囲、重大度「0：重大」で絞り込みます。
2. Critical の発生後、取り込みと5分間隔の評価を待ち、`alert-arclab-windows-critical` のアラートを開きます。
3. 状態が「発生（Fired）」で、ディメンションの `Computer` が対象サーバーであることを確認します。
4. メール通知を試す場合は、受信メールの規則名、重大度、コンピューター名を確認します。既存の `9001` の通知や、アクショングループのテストメールとは区別してください。

### Critical が発生していない場合

- **本番サーバーの強制電源断、OS 障害、サービス障害などを起こして Critical を生成しないでください。**
- 実イベントがない場合は、**「アラート規則の作成・保存確認済み、Critical による発報は未確認」**と記録します。アクショングループの「テスト」でメールが届いても、Critical による発報を確認したことにはなりません。

### 再通知と自動解決

本章は既存手順と同じく、自動解決を有効にしたステートフル アラートです。同じ `Computer` のアラートが Fired の間は、Critical が追加されても新しい発生通知は送られません。再通知を試す場合は、Resolved になった後に新しい Critical が必要です。

最後の Critical が15分の検索範囲から外れ、その後の5分間隔の評価で3回連続して条件を満たさなくなると自動解決します。ログの取り込み、評価、通知の時間も考慮してください。イベント1件ごとの再通知が要件であれば、本章とは別に通知方式を設計します。[^3]

## 5-3. 演習後の扱い

- 継続運用する場合は、通知先、重大度、検索期間、担当者を確認してください。
- 演習用の規則が不要になった場合は、`alert-arclab-windows-critical` だけを無効化または削除します。
- 既存の `9001` 用規則、LAW、DCR、AMA、共用アクショングループは変更・削除しません。
